# 系统评估与本次收敛

## 结论

保留 11 个专业角色与 16 项技能，不继续堆角色。系统的价值是章节交接、人物选择、持续状态和证据化复核；脚本的价值在确定性检查，不在替代审美。当前不应称为已验证的顶级自动写手。

## 已处理的有限问题

- 分发依赖：市场资源不能依赖不随方案上传的工程目录。必要的五份文档模板归属到各自技能，按触发条件读取；脚本仅在独立完整版中保留。
- 检查器误拒：允许技能内真实存在的附件，测试覆盖缺失及越界路径。不是把“禁止一切附件”当成安全。
- 连续性输入：章节包要求提供必要原文、人物知识和关系压力，不能只传摘要文件名给无工具正文作者。
- 创作自由：模板只限定事实与结果边界，不固定动作、对白、情绪表达和段落节拍；沿用作品已有格式，不每章重做人物履历。
- 状态更新：用户批准必须对应当前稿件；变化须有正文依据并避免重复入账。无保存工具时交付文本，不伪称持久化。
- 版本隔离：市场方案、脚本增强源码、个人作品与历史回滚分开。公共模板不得混入真实书稿或个人运行记忆。

## 仍需真实使用证明

已核对当前安装的 FeelFish 内置工具定义：get_file_info 支持字数与成对起止行。市场版将其授予上下文管理员，不要求为单纯字数统计安装脚本；实际返回口径与调用成功仍需宿主运行验证。

模型调用是否成功取决于宿主与服务；总导演调度及技能触发需要真实会话验证。程序只能发现部分重复、字数和结构化状态问题，不能证明情绪动人。长期状态提取准确度、跨章文风、修订收益、成本与缓存需要实际数据，不通过扩大提示词或增加审稿轮数解决。

建议首次使用只走“已存在资料→一份最小章节包→一版正文→有证据的局部复核”，不生成多版本正文竞赛，不因资料多而全文读取。已有草案的“建议”不得自动升级为正式设定。
