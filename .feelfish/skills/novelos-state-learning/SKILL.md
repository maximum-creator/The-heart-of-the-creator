# 状态提交与持续学习

## 两阶段提交

1. 从最终候选稿提取状态差量，先写入 `NovelOS/05-chapter/state-delta-proposal.md`。
2. 分类为：已有事实、正式状态变化、候选 Canon、临时细节、角色说法、研究待核项。
3. 对照硬审计报告，确认没有 P0。
4. CALIBRATION 阶段只有用户明确说“批准定稿”后才更新；PILOT/PRODUCTION 阶段可由完整的自动验收回执批准，不能把模型自评当批准。
5. 先更新 `NovelOS/04-canon/entity-state-ledger.json`，通过审计后运行 `render-state-ledger.mjs --write` 生成 `entity-state-view.md`；其他专题 Markdown 只保存需要细读的证据和解释。提交后记录章节号、旧值、新值、证据段落和提交时间，不得覆盖历史原因链。

另存机器可审计的 `state-delta-proposal.json`：必须绑定最终稿 SHA-256，每项关键变化引用不超过 80 字的正文原句。运行 `transition-contract-audit.mjs` 对照章前契约；变化没有发生、进展被系统/巧合代办、保护事实漂移、活跃问题被无证据抹平或引用并不存在时，一律不提交。该检查复用本轮状态提取，不增加一个模型调用。

提交前委派工具管理员运行 `novelos_state_audit`，交叉检查人物在场与地点、物品持有人、知识来源、金钱余额、伤势恢复窗口和伏笔推进窗口。`HARD_FAIL` 阻止提交；`REVIEW` 只是待核位置，不能当成质量分、不能触发自动剧情修改。

## 必须维护

- 事件与因果。
- 人物和关系当前状态。
- 角色知识及知识来源。
- 时间、地点、物品、能力、伤势和金钱。
- 伏笔生命周期与读者承诺。
- 候选长期事实。
- 最近五章的开场入口、注意力/感知路径、对话控制者、冲突解法、代价、章末动力和有意回环用途；只记摘要与证据位置，不复制正文。
- 获批正文中真正改变人物辨识度的注意力、词汇边界、关系姿态或压力策略，更新到声线与注意力账本；一次性的漂亮句子不晋升为永久口头禅。

## 学习闭环

用户的“好看、无聊、很 AI、人物假、不想看下一章”先转为候选原因。单次反馈不能直接成为永久规则；多次复现、正文证据或平台数据支持，并经自有章节 A/B 测试后才能晋升。活跃错题保持少量，其余归档。模板见 `assets/state-delta-template.md`、`assets/error-card-template.md` 和 `assets/success-card-template.md`。

不得因为指纹工具命中就自动更新永久规则。刻意回环、角色口头禅和主题意象要记录“本次改变了什么意义”；答不出来才列入下一章避免项。

批准后的结构变化还要检查它影响的抽象层：人物状态、当前卷目标、近期章节窗口、伏笔/承诺和简介卖点。只传播有证据的结构影响，不让每句对白触发全库更新；发现冲突时标为待决定，不擅自把正文改回旧大纲，也不把旧大纲静默改成“早已如此”。

### 番茄真实数据归因

- 只读取异常跌点前后的最小章节窗口，不整本灌入上下文。
- 同时记录曝光、人均阅读时长、章节流失、追读及发布时间；不能把单个跌点直接归罪于某一句话。
- 区分文本因素与书名封面、推荐流量、断更、样本量和章节长度等混杂因素。
- 用户亲自改写是高权重的个人偏好证据，但不是全市场通用真理；与平台数据互证后再晋升为规则。
- 每次实验只改变少量可辨认变量，记录改前假设、改后窗口、成本和结论；证据不足时保留为 OPEN，不强行总结。
